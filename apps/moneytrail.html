How this works

        
One governed graph query per surface — no warehouse, no pipeline, no model making up numbers.


        
The graph is virtual

        
Nothing you see here was mirrored into a database. When a surface needs an answer, it
           invokes a named Lens — a governed query over a graph whose nodes are fetched from
           the government's own APIs at question time, cached briefly, and rolled back after. Pin a
           contract notice by its id and the traversal below is the passport page:

        
MATCH (n:ContractNotice {cnId:'CN3942784'})-[:HAS_VERSION]->(v:ContractVersion)
RETURN v.releaseDate, v.amount, v.tags, v.supplierName, v.agencyName
ORDER BY v.releaseDate
// The anchor seeds a live fetch from api.tenders.gov.au — one call, every published
// version of the notice, values as amended. No AusTender export was harmed.

        
The engine plans the external work before doing it: calls are budgeted against each
           source's declared rate, a fetch that would exceed the budget is deferred and
           labelled rather than silently truncated, and an observed rate-limit backs the
           source off adaptively. That is why the period scan says PARTIAL when it means
           partial — the honesty is enforced in the engine, not requested in a prompt.

Why this is hard without a graph engine

        
The AusTender API filters by nothing but id and date — no agency, supplier, ABN or
           text search exists. A dashboard over it either mirrors the whole register (and goes
           stale) or can't answer supplier-shaped questions at all. Virtual Cypher fetches the
           slice each question needs, joins it to other registers at query time, and stamps
           every hop with its source, licence and as-at date. When a fetch fails, the answer says
           unknown — a failed lookup and a genuine zero never render the same way anywhere
           in this app.
